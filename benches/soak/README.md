# 8 小时 soak 基线（V-H05 / PERF-04，v2.1 §32.1 Soak）

由 `xtask/soak` 跑出。这里记的是人读过的数字，以便以后的回归是一次 **diff** 而不是一场争论。

## 跑什么，为什么是四种负载

§32.1 点名四种，它们漏的东西各不相同：

| 负载 | 它会漏掉什么 |
|---|---|
| 高频命令 | decoder 缓冲、result record |
| 连接切换 | socket、每连接状态、task handle |
| 消息流 | push 环形缓冲、订阅簿记 |
| 反复开关 TUI | 终端所有权、布局缓存、alternate screen |

进程每 10 秒给自己采一次样，写一行 JSON。**这样这次运行在还没跑完的时候就能被分析**——
一个要到第八小时才知道结果的测试，是一个你只会跑一次的测试。

```bash
cargo run --release -p soak -- --hours 8 --out soak-metrics.jsonl --redis 127.0.0.1:6379
```

不给 `--redis` 时命令与 push 两种负载打合成 RESP server，所以这个 runner 在一台没有 Docker 的
机器上仍然有用。

## 判据：线性增长，而不是「内存变大了」

`xtask/soak/src/lib.rs` 对每条指标做最小二乘拟合，**只有当总变化量超过残差标准差的 3 倍时才判为
增长**。一台跑着别的东西的机器上，RSS 上下几兆是常态；把那个叫泄漏，等于让这个测试每次都红，
然后被人关掉。

还有一条反向判据：**命令计数必须是 Growing**。没有它，一个在第二分钟就崩掉的 runner 会报告
一条完美平坦的内存曲线。

`xtask/soak/tests/growth.rs`（8 tests）单独测这套判据：平的、带噪声的平的、慢泄漏、噪声里的
泄漏、锯齿、太短的样本、停住的运行、任务泄漏。**先证明检测器会响，再拿它去听。**

## 它抓到的第一件事（跑起来 70 秒之内）

`pr-core::TaskScope::spawn` 把每个 `AbortHandle` 推进 `Vec`，只在 shutdown 时清空。于是一个
长命的 scope 上，句柄以约 **60 KB/s** 的速度堆积——八小时 1.7 GB。

单元测试看不见它：一个测试里的 scope 活几毫秒。soak 的第一次正经运行 70 秒就把它摆了出来，
堆从 100 KB 涨到 4.3 MB。修法是 `prune_finished()`（句柄数超过 64 且超过活跃任务两倍时回收
已完成的），加两条回归测试，其中一条断言**还在用的句柄不会被回收掉**——一个只证明「数量变少了」
的修法，可以用「把它们全删掉」来通过。

修完之后，同样的负载下堆稳定在 ~100 KB。

## CI

`.github/workflows/ci.yml` 的 `soak` job，`schedule`（每天 03:00 UTC）与手动触发，不在 PR 上跑。

§32.1 要的是八小时；**GitHub 托管 runner 六小时会杀掉任何 job**，而且 release build 要先跑完，
所以 CI 跑五小时，八小时那一份证据来自一台跑得动的机器（上面那一节，JSONL 一并存档）。
分析、阈值、退出码两边完全一样，不一样的只有窗口长度——这一点写下来，而不是抹掉。

`workflow_dispatch` 带一个 `hours` 输入，所以这个 job 本身可以用十分钟验一次。
**一个五小时的 job，如果它的第一次运行同时也是它的第一次测试，那就是一种花五小时找错别字的方法。**
