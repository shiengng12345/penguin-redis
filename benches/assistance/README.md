# Assistance 堆增量实测（V-F09，v2.1 §12.5、§16.4、§24.7、R08、R35）

工作集在 `crates/pr-intelligence/src/working_set.rs`；堆称重在 `crates/pr-intelligence/tests/working_set_heap.rs`（3 tests）；行为规则在 `crates/pr-intelligence/tests/working_set_budget.rs`（4 tests）；RSS 差在 `crates/prc/tests/budgets.rs` 的三个 `f09_*`。

## 2026-09-16 — Apple M3, macOS 26.5.2 (aarch64), rustc 1.97.1, debug build

| 量法 | 数值 | 预算 | 余量 |
|---|---:|---:|---:|
| **RSS 差**（§12.5 字面要求的量法：开/关提示两个子进程） | **8.53 MiB** | 12 MiB | 3.47 MiB |
| **堆**（计数 allocator，饱和工作集） | **8.84 MiB** | 12 MiB | 3.16 MiB |
| 缓存自报 | 9.71 MiB | — | — |
| 空工作集 | **0 B** | — | — |
| catalog 单独报告 | 5.06 MiB | — | 不计入增量 |

两个量法互相印证（8.53 / 8.84），这才让任何一个可信。**用两个仪器是因为它们的失效方式不同**：进程内的泄漏会出现在 allocator 上而可能不出现在 RSS 上；allocator 的自身开销会出现在 RSS 上而不出现在 allocator 上。

`catalog` **在差值的两边**，因此自动抵消——§24.7 要求「不含只读 mmap catalog」，这是按构造排除的，不是靠减法，并且有测试检查这个构造（两个探针都必须看到 586 条命令）。

## 测的是饱和后的工作集，不是空闲的

每一个 §12.5 子项都被填到它自己声明的上限——**仍在预算之内**的最坏情况。空工作集的成本是 **0 B**：12 MiB 是「可以长到多大」的上限，不是启动时的预留。

子项也逐个称重，不只看总数：一个通过的总数可以掩盖一项超 2.5 倍、由另一项只用一半来补——而超的那一项，正是用户的 keyspace 形状与 fixture 假设不同时会长起来的那一项。

## 测量本身的两个 bug（都是真的，都修了）

**第一个：并行测试下的全局 allocator 计数是无意义的。** 第一版量出 22.9 MiB，而工作集实际是 8.8 MiB——因为同一个二进制里的另一个测试当时正握着 8 MB 的 fixture，Rust 默认并行跑测试而计数器是进程全局的。修法：把称重测试单独放一个二进制，并用 mutex 串行化。**一个量错了的预算检查，比没有检查更糟**，因为它看起来像证据。

**第二个：`BoundedNames` 和 `ObservationStore` 都只数了存进去的字节，没数容器自己的开销。** 实测：一个声称 2 MiB 的 field 缓存实际占 5.2 MiB。差额全部是预算没数的记账——每条 48 字节的 `(Vec, Vec)`，加上一个容量已经翻倍到超出在用量的 `Vec`。

> **一个不数容器开销的预算不是预算。** 预留但未使用的容量是常驻内存，进程要为它付钱，无论这个缓存承不承认。

修法：`bytes()` 计入 `capacity() × size_of::<slot>()`，驱逐判据也用它。修完之后自报值变成**保守的**（9.71 ≥ 实测 8.84），这是预算该有的方向——宁可高估，不可低估，并且有一条断言守住这个不等号。

## §12.5 的两项限额，两半都要执行

**已观察 key 名缓存：「5,000 个或 2 MiB，先到者为准」。** V-F09 发现这个 store 只执行了条目数那一半——5,000 个 40 KiB 的名字会在一个 2 MiB 的预算里握住 200 MB。两半现在都执行，并且各有一条测试证明它会先到：普通名字由条目数卡住，长名字由字节数卡住。

**单条超过整个预算的名字被拒绝，而不是清空缓存去腾地方**（「超长名字受单项限制，仍可手输」）：为一个 3 MiB 的名字腾出 2 MiB 的缓存，意味着丢光一切并且仍然装不下。

**field/member 缓存是「2 MiB 总预算」，不是每 key 2 MiB**（「分 target/key LRU，不按每 key 无限叠加」）：按 key 算预算的话，一百个 key 就能握住一百倍。有一条用 100 个 key × 1,000 个 field 的测试守住。

驱逐数**对外暴露**，不是悄悄忘掉：一个默默遗忘的缓存，从外面看起来和一台丢了 key 的服务器一模一样。

## 没有调整预算，所以没有 ADR

V-F09 的回退条款是「超出 → 先定位；预算调整必须带证据与 ADR」。没有超出，12 MiB 不动。上面两个修复是**记账的正确性修复**，不是预算调整——它们让实际占用向下走了，不是让上限向上走。

## 还没做的

- **只读 mmap catalog**：目前 catalog 是嵌入二进制的，不是 mmap 的。§12.5 的「目标 ≤ 6 MiB 文件、由 OS page cache 管理、多进程可共享页」要等 catalog 改成 mmap 之后才谈得上，那时要重测并单独报告。现在如实记的是「嵌入式 catalog 的 RSS 份额 5.06 MiB」。
- **真实使用下的增量**：这里测的是人工饱和的工作集。Phase 2 有了真实补全流量之后，要用同一对探针重测一次，看真实分布下哪个子项先满。
- **Release build 的数字**：本表是 debug。CI 断言的也是 debug，这是保守方向——debug 更大更慢，debug 过了 release 必过。
