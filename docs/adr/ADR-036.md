# ADR-036 · 「粘贴绝不自动执行」不依赖终端能力：bracketed paste 与 10 ms 时序启发式是两条并存的路径，`plain-only` 是最后手段

- **状态**：accepted
- **日期**：2026-09-16
- **依据**：v2.1 §14.1、§24.3、§32.6、R05、ASSIST-082、UX-11
- **Phase 0 验证项**：V-C03、V-J04

## Context

§14.1 只要求一件事：**粘贴的内容绝不自动执行**。它能不能做到，取决于终端发不发 `CSI ? 2004` 的成对标记——而这是我们控制不了的变量。计划给的回退条款是「某终端两者皆失败 → 标 `plain-only`」。

问题在于「两者」是哪两者，以及一个不发标记的终端是不是就此变成二等公民。

## Decision

两条路径**并存**，不是主备：

1. **bracketed paste**（精确路径）。启动发 `CSI ? 2004 h`，退出发 `CSI ? 2004 l`；成对标记之间的内容进 paste-staging。
2. **10 ms 时序启发式**（无标记时）。到达间隔构成的 trace 被判为粘贴时，同样进 paste-staging。

两条路径通向**同一个** staging 视图，因此「不自动执行」这条不变量不随终端能力变化。多行进审阅视图逐行显示，可上下移动、编辑、删除，出口只有三个（逐条提交 / 单条多行提交 / 取消）；**Enter 在该视图中刻意无作用**——用户凭反射会按的那个键，正是此刻必须什么都不做的键。单行粘贴直接进编辑缓冲区，不提交。

**`plain-only` 是最后手段，不是第一选择。** 一个终端只有在 bracketed 与时序**两条路径都已证明失败**之后才能这样标；在那之前，正确反应是把该终端的真实到达间隔录下来（`script` / `cat -v`）加进 corpus 并调阈值。

**半对标记（只收到起始或只收到结束）按无标记处理**，并在支持矩阵注明。半对比没有更危险：结束标记丢失会让后续键入被当成粘贴内容。

## Consequences

- 时序启发式覆盖不了的情形是存在的——慢速中继转发的粘贴，逐字节到达间隔与打字无异。这一条以一个**断言它确实漏检**的测试写明，而不是从报告里省掉。一个被记录的盲区可以被后续工作缩小；一个被省略的盲区会在用户那里被发现。
- 人工记录（`MV-V-C03-*`）覆盖自动化无法覆盖的那一半：仿真 PTY 里的标记是我们自己发的，它当然成对。编号已分配，未执行；**不阻塞 Phase 1**，因为「不自动执行」在两条路径上都已自动化验证。
- 记录表里第 4 项（有没有命令自己跑掉）若为「是」，是 P0 bug 而不是「该终端不支持」。这条写在模板里，因为把 bug 记成能力差异是最省事的那个选择。

## 结果 / 验证记录

**PASS**（2026-09-16，V-C03）。

- bracketed 路径：真实 PTY 上粘贴 3 行含 `FLUSHALL`，删掉那行再选「逐条」，只有另两条被提交。
- 时序路径：14 条定时 trace corpus 上 **0 漏检**，误判 **0 / 7（0%）**。corpus 覆盖瞬时、1 ms、CRLF、纯 `\r`、10 行脚本、超长单行，以及正常打字、快速打字（15 ms）、犹豫打字、按键重复、刚好 11 ms 的边界。
- Windows 上这条 ADR 曾**真实失效过**：crossterm 在 Windows 不产生 `Event::Paste`，粘贴以普通按键（含 Enter）到达，三条命令全部自动执行——包括 `FLUSHALL`。时序启发式当时只是一个纯函数，从未接到实时输入路径上。见 [ADR-035](ADR-035.md) 发现 3。
