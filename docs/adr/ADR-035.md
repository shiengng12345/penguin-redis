# ADR-035 · Windows Terminal / ConPTY 是一级目标，conhost 是 plain 模式降级目标；`SetConsoleCtrlHandler` 的 OS 投递层延至 Phase 1

- **状态**：accepted
- **日期**：2026-09-16
- **依据**：v2.1 §35.1、§32.1、§22.3、R20
- **Phase 0 验证项**：V-C07、V-J04

## Context

§35.1 把 Windows 分成两档：Windows Terminal（ConPTY）是一级目标，legacy conhost 是 plain 模式降级目标。Phase 0 之前，这个分档从未被执行过——`xtask/pty-harness` 自己的测试在 Windows 上全部 `#[cfg_attr(windows, ignore)]`，注释写着「V-C07 covers Windows」。也就是说，一整条平台路径的状态是「假设可行」。

SPIKE-003（V-C07）是第一次真跑 ConPTY。

## Decision

**Windows Terminal / ConPTY 是一级目标**，并且是 CI 上实际执行的那一条：`windows-latest` runner 通过 ConPTY 运行 `pty_owner.rs`（11）、`key_matrix.rs`（4）、`width_matrix.rs`（12）与 `pty-harness` 自己的 36 个测试。三平台 PTY 测试不再有 `cfg_attr(windows, ignore)`。

**legacy conhost 是 plain 模式降级目标**，实测属于 `MV-V-C07-*` 人工记录；若不达标按 §35.1 标 `plain-only`，不影响一级目标的结论。

**`SetConsoleCtrlHandler` 的 OS 投递层延至 Phase 1**，且这条限制以「未接线」的形式明写在 SPIKE-003 与本 ADR 中，而不是让它看起来已经完成。含义层（§22.3 的六种 Ctrl+C 语义、Ctrl+Break ≡ 两次 Ctrl+C）已实现并有 9 个测试；缺的是把 OS 事件送进来的那一段，它需要一个封装 `unsafe` 的 crate，而 workspace 是 `unsafe_code = deny`，选哪个 crate 属于供应链决定（ADR-023）。在那之前，raw mode 下 Ctrl+C 作为普通按键到达并已生效；**只有 Ctrl+Break 这一条路径尚未接通**。

## Consequences

- Windows 不再是「最后再看」的平台。三个真实缺陷在 Phase 0 被抓到并修掉，而不是在 Phase 2 的终端工作写了几千行之后一起爆出来。
- Ctrl+Break ≡ 两次 Ctrl+C 的实现方式是**把规则跑两遍**，不是给结果开特例——于是两种写法不会随 §22.3 的演进而分叉，`ctrl_break_is_exactly_two_ctrl_c_and_not_a_special_case` 对七种活动状态逐一对照两条路径。
- `pty-harness` 现在会代终端回答 ConPTY 的启动查询，这一行为记为 `Event::AutoReply` 而非 `Event::Input`，golden 因此能分清哪些字节是测试发的。

## 结果 / 验证记录

**PASS**（2026-09-16，V-C07 / SPIKE-003）。

| 项 | 状态 |
|---|---|
| WIN-01（PTY 场景同一套 fixture 在 ConPTY 下通过） | **PASS** |
| WIN-02（二进制 stdio，无 CRLF 转换，bytes 往返一致） | **PASS** |
| Ctrl+C 语义（§22.3 六态 + 退出码区分） | **PASS** |
| Ctrl+Break ≡ 两次 Ctrl+C（含义层） | **PASS** |
| `SetConsoleCtrlHandler` OS 投递层 | **未接线**，依赖 ADR-023 的 crate 选择；限制已记录 |
| legacy conhost | `MV-V-C07-*` 人工记录待执行；非一级目标 |

三个被 Windows CI 抓到的真实缺陷，全部已修并有测试守住：

1. **ConPTY 启动时阻塞等待光标位置报告（P0）**。7 个 PTY 测试全部超时，收到的字节数是 **4**：`ESC [ 6 n`。ConPTY 发出 Device Status Report 并**阻塞**，直到持有 pty master 的终端回答；我们的 harness 从不回答，于是子进程一个字节都出不来。修法是 reader 线程识别该查询并回 `ESC [ 1;1 R`（不追踪真实光标——提问的程序要的是一个格式正确且及时的答案），查询可能跨两次 read 被切开，因此带 3 字节 carry。
2. `crossterm` 在 Windows 上同时投递 `KeyEventKind::Press` 与 `Release`，每个字符被输入两次。translate 搬进 `pr-terminal::bridge` 并加 8 个测试。
3. **粘贴的三条命令全部自动执行，含 `FLUSHALL`**——crossterm 在 Windows 根本不产生 `Event::Paste`，粘贴内容以普通按键（含 Enter）到达；时序启发式此前只是一个纯函数，从未接到实时输入路径上。这一条与 V-C03 / [ADR-036](ADR-036.md) 是同一件事。

**这个诊断是怎么来的**值得单独记一笔：`PtyError::Timeout` 原先只说「等什么超时了」。改成同时带上「实际收到了什么」之后，第一次 CI 就给出了答案。一个不说收到了什么的超时，在你无法 attach 的 runner 上近乎无用。

证据：`docs/spikes/SPIKE-003.md`、Windows CI 上的 `pty_owner.rs` 11 + `key_matrix.rs` 4 + `width_matrix.rs` 12 + `pty-harness` 36 tests、`crates/prc/src/binout.rs` 4 tests + `win_02_binary_output_reaches_a_pipe_byte_for_byte`、`crates/pr-core/src/signal.rs` 9 tests。
