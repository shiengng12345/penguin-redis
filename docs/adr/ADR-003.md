# ADR-003 · 无必需 backend / daemon；Core 是链接进可执行文件的库

- **状态**：accepted
- **日期**：2026-09-16
- **依据**：v2.1 §2、§12.10、§35.2、LIFE-01
- **Phase 0 验证项**：V-H04、V-H05、V-D08

## Context

用户不接受为了一个 CLI 先启动服务、Docker 或 GUI。退出后不能留下自己的后台负担。

## Decision

`pr-application`/`pr-core` 等全部是 library；`prc` 单进程；无监听端口、无计划任务、无索引器。SSH tunnel、MCP 子进程只在明确启用时存在并随进程退出。所有预算为进程级（ADR-029）。

## Consequences

跨进程共享只能通过只读文件 + OS page cache；不承诺跨进程速率聚合；`--mcp-stdio` 由 host 拉起。

## 结果 / 验证记录

**V-H04 → PASS**（2026-09-16）。证据：`crates/pr-core/tests/task_soak.rs`（10 tests）、`crates/prc/tests/tui_cycle.rs`（3 tests，PERF-03 1000 次开关）。

验证过程修正了 `TaskScope` 的取消语义。原实现在 spawn 的包装里用 `select!` 让 cancellation token 与用户 future 竞速：token 一取消就 drop future，于是 §31.1 要求的「先 cancel 令牌 → 有界等待 → abort」三步里，后两步全成了空转——协作式清理从来没机会运行，`shutdown` 也对永不退出的任务报告 `drained = true`。现在包装只负责 RAII 计数，token 纯粹是信号，`abort` 是超时后的硬停止；`shutdown` 返回 `true` 表示每个任务都自己走完了，返回 `false` 表示至少一个被强杀、其清理未必跑过。
