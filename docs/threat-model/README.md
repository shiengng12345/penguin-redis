# 威胁模型：信任边界（V-J03）

> v2.1 §23、§33。**通过标准是「无未覆盖边界」。**

## 这份文件与 `boundaries.toml` 的关系

清单在 `boundaries.toml`，是机器可读的。这份 md 是给人读的说明。

「无未覆盖边界」不是这里写一句就算数的——它由 `crates/pr-security/tests/threat_model.rs` 的 8 个测试强制，而且是**双向**的：

1. 每条边界至少有一个 SEC 用例
2. **每个 SEC 用例至少被一条边界认领** —— 没人认领的用例是一个「通过了但没人知道它在保护什么」的测试；等它哪天开始失败，也没人知道坏的是什么
3. **每条边界引用的文件必须真实存在** —— 引用一个已被改名的路径，等于一条已经悄悄变成假话的覆盖声明
4. 每条边界必须说明**跨越它的代价**，而不是复述自己的名字

## 什么算「信任边界」

数据从我们不控制的地方，进入我们控制的地方。

这个定义刻意宽。它把「服务器返回的错误文本」和「用户敲的那一行」放在同一张表里，因为两者都不是我们写的，而且都会变成我们要负责的东西。

## 边界清单

| id | 边界 | 跨越了什么 | SEC 用例 |
|---|---|---|---|
| `input` | what the user types | a person's keystrokes into an argv the kernel will send | SEC-02、SEC-10 |
| `parser` | bytes off the wire | server-chosen bytes into the decoder | SEC-07 |
| `config` | profile and configuration files | a file on disk, possibly written by something else, into connection and policy decisions | SEC-04 |
| `connection` | who answered | a TLS identity and a service identity into a decision to send a credential | SEC-05 |
| `errors` | error text from the server | server-authored text into a terminal, a log and an exit path | SEC-01、SEC-05 |
| `trace` | wire traces and debug output | everything on the connection into a file the user may share | SEC-01 |
| `history` | the command history file | commands the user ran into a file that outlives the session | SEC-01 |
| `clipboard` | copy to the clipboard | a value from the result store into every other application on the machine | SEC-08 |
| `export` | writing results to a file | server data onto the local filesystem | SEC-08 |
| `crash` | panics and crash reports | in-memory state, including secrets, into a report or a core file | SEC-07 |
| `suggestion` | what the assistance engine offers | observed server data back into a command the user is about to run | SEC-06 |
| `metadata` | server-reported command metadata | a server's claim about what a command does into a policy decision | SEC-11 |
| `plugin` | renderers and adapters | third-party code into the render path | SEC-07 |
| `mcp` | an agent over MCP | a request from a program into the same kernel a person uses | SEC-03、SEC-06、SEC-09 |
| `pipe` | frames from --pipe stdin | a byte stream, possibly generated by another program, into commands | SEC-09 |

## 三条最容易被漏掉的

**`suggestion`** —— §23.7 专门把它称为**新的**信任边界，因为它不像一条边界。补全菜单里的 key 名来自服务器返回的数据；用户接受一条补全，就是服务器影响了用户下一条要发什么。守住它的是零发送不变量（`zero_send.rs`）与「value 位永不枚举观测数据」（§12.2）。

**`metadata`** —— 服务器可以在 `COMMAND` 里声称一条写命令是 readonly。如果本地策略采信，那么这个守卫就变成了它本该防范的那个东西可以控制的。方向是单向的：远端只能标注 `unknown`，不能放宽（`precedence.rs`）。

**`crash`** —— panic 消息由当时作用域里的东西拼出来。一条会格式化 `CommandRequest` 的崩溃路径，就会把它的参数一起格式化，其中可能包括 `AUTH` 的密码。

## 边界之间不是独立的

`connection` 决定凭证发给谁，`config` 决定 `connection` 怎么解析，`mcp` 可以请求任何一条命令。一条边界被攻破，往往让下一条变得更容易跨越——所以 `covered_by` 引用的是**类型与测试**，不是文档段落。类型系统不会因为读的人赶时间就放行。
