# 人工验证记录模板（P0-META-03）

> 用于无法自动化的验证：系统 IME、屏幕阅读器、真实终端字体宽度、bracketed paste 实测（v2.1 §32.6）。  
> 人工记录**同样是发布门禁**，不是「支持 Unicode」一句话的替代品。  
> 编号规则：`MV-<V项>-<平台>-<序号>`，例如 `MV-V-C03-macos-iterm2-001`。ASSIST / UX 案例引用该编号作为证据。

---

## 先问一句：这条记录真的必须由人来做吗？

有些终端可以被脚本驱动而仍然是**真实终端**。kitty 有 remote control：
`send-text --bracketed-paste auto` 只在窗口里的程序真的打开了 DECSET 2004 时才包标记，
`send-key` 走它自己的按键编码器，`get-text` 读回真正渲染出来的屏幕。
[`ci/terminals/record-kitty.sh`](../../ci/terminals/record-kitty.sh) 就是这样采集
`MV-V-C03/C04/C05-macos-kitty-*` 的，产物存档在 [`records/`](records/)。

这样得到的记录比人手敲的强三点：它**可重复**（复核 = 再跑一次然后 diff，而不是看录屏）、
它**不会记错**（屏幕原样存档）、它**会回归**（终端升级之后重跑就知道有没有变）。
V-C04 的那个缺陷正是这么抓到的——一个真实终端回答了 `CSI 6 n`，而我们的读取路径把它丢了；
任何单元测试都看不见，因为假终端永远会回答。

所以顺序是：**先问能不能脚本驱动，不能再叫人。** 剩下真正只有人能答的，是 OS 与输入法那一层
（remote control 从终端内部注入，绕过它），以及没有 remote control 的终端。

> 用脚本采的记录，「复核方式」填 `复现（重跑脚本并 diff）`，并写明脚本路径与产物路径。
